# ジャンル・要素の全件見直し (= トリガー「見直し流して」「見直し点検して」「見直しどこまで」)

全69,556頁を1行ずつ並べた「見直しの表」の順に、手元の材料(楽天・BookLive の紹介文)を Haiku が読んで、
ジャンル・要素の**付与案**を作る。★案を作るだけ。本番データ・seed には書かない(書くのは別工程・ユーザの Go・Opus)。

- 判定は道具が Haiku を「土台なし」で直接呼ぶ。運転者(このセッション)は**コマンドを打って出力を貼るだけ**。材料を自分で読んで判定しない。
- 進み具合は台帳(`data/element-harvest/review-ledger.jsonl`)に残る。止めても次は続きから。
- 経緯・裁定・数字 = memory [[element-review-queue-state]]。判定の決まり = `scripts/_element-assign.py` の `RULES`(skill `element-assign`)。

## ★進め方(2026-10-13 ユーザ裁定): 最後まで流す → まとめて見直す

「完璧な物を一回で作るのではなく(多分無理)Sonnet だけで効率的に進めて。最後までやって、また見直す」。
- **流している間は道具を直さない・判定し直さない**。点検は報告を**貯めるだけ**(`data/element-harvest/inspections/`)。Opus は呼ばない。
- Sonnet の窓の日課 = 「見直し進めて」: **流す → 点検1回 → commit+push** を、使用量の上限(■ 中断)か「未」が尽きるまでくり返す。
  - ★流すコマンドは `python scripts/_element-review.py run --n 100 --until 1000 --twice`(= **点検待ちが1,000件に届くまで**)。途中で止まって再開しても、足りない分だけ流す。
    点検待ちがもう1,000件以上なら1件も流さずに終わる = そのまま点検へ(2026-10-14: 921件で止まった後の再開が、新しく1,000件を始めていた)。
  - ★**件数は出力の最後の「==== 今回の合計 ====」の行から取る**(報告にも commit の題にも)。途中の「== 回 … の要約 ==」は100件ごとの小計で、最後の回の件数は全体ではない
    (2026-10-14 実害: 921件を「21件」、943件を「43件」と報告し、ユーザに「全く進まなくなった」と読ませた)。
  - 中断で終わった回も、点検待ちが30件以上あればその場で点検する(点検はモデルの上限と関係なくこの窓でできる)。
  - ★点検は約1,000頁の**ロットの抜き取り検査**。30頁を読み、残りは機械で数えて、ロット全体を点検済みにする(設計どおり・バグではない)。だから点検の後は点検待ちが0になり、次の流しがまた約1,000件流す。
    流した件数が1,000を超える(1,200〜1,300件)のも正常 = 材料なしの頁は点検待ちに数えない。 2026-10-21 Haiku の窓が「pool を pick に直し、点検の記録を消す」と提案した = **しない**(直すと流しが30件ずつしか進まなくなり、記録も失う)。
- 途中で止めて Opus に回すのは**壊れている時だけ** = 点検の30頁のうち問題なしが15頁未満、または「語が全部消える/全頁に同じ語」のような機械の不具合。それ以外の型は報告に書いて先へ進む。
- 経路L を流し切ったら「見直しまとめて」(Opus): 貯まった報告を全部読み、型をまとめて1回で直す。
  - 機械の決まり(2回の合わせ方・語彙・隠す語・ジャンル案の条件・語の重なり)= `python scripts/_element-review.py rebuild`(モデルを呼ばない・全頁 数分・0円。2回の生の答えを各頁に残してあるので何度でもやり直せる)。
  - 判定の決まり(指示文 RULES)を変える時だけ判定し直しが要る = 効く頁を絞って `run --stems`。全件の判定し直しはしない。
- ★だから流している間の「惜しい誤り」は急がない。生の答えさえ残っていれば、後から全頁に直しが効く。

## 「見直しどこまで」

```
python scripts/_gen-element-review-queue.py      # 表を作り直して、経路ごとの 未/案あり/適用済 を出す(約15秒)
python scripts/_element-review.py summary        # 回の一覧
```

出力をそのまま貼る。経路 = A(アニメ化あり)/ L(手元に材料あり)/ W(材料なし = ユーザ裁定で当面保留)/ 後(もう要素3つ以上)。

## 「見直し流して [件数]」(件数なし = 500)

```
python scripts/_element-review.py run --n 100 --loops <件数÷100> --twice
```

- ★60秒を超える。**background で起動し、途中で覗かない**(100件 約25分・約280万トークン。起きるのは終わりの1回)。skill `long-job-ops`。
- `--twice` = 同じ頁を2回判定させて合わせる(芯+芯・芯+在る → 表 / 片方しか挙げない語 → 隠して持つ / 材料からのジャンル案は2回とも芯の時だけ / 表が0語になる頁だけ 在る+在る の語・片方だけ芯の語を最大3語 表に上げる)。外さない。
- 終わったら、最後の「==== 今回の合計 ====」の行をそのまま貼り(件数はこの行の「流した」。各回の要約は小計)、台帳を commit+push:
  `python scripts/_gen-element-review-queue.py && git add data/element-harvest && git commit -m "ジャンル・要素の見直し: 経路L <件数>件(案のみ)" && git push`
- 「■ 中断」(モデルの失敗が3件 = 使用量の上限かもしれない)が出たら、そこで止めて報告する。叩き直さない。中断でも「今回の合計」の行は出る = 済んだ件数はそこから。
- ★ユーザが自分で流す時(見張りのトークン0)= ふつうのターミナルで上のコマンドをそのまま打つ。

## 「見直し点検して」(= Sonnet の仕事。1,000件に1回が目安)

1語ずつの当否は2回判定で済んでいる。ここで見るのは**誤りの「型」**(同じ癖で何頁にも出る間違い)。
★報告は会話に書かず**ファイルに書いて push する**(直す側の窓が読めるように。2026-10-13)。手順は3つだけ:

```
python scripts/_element-review.py inspect        # ① まだ点検していない頁から30頁を抜き取り、報告の書き込み先(.md)を作る
```
② 出力に出たファイル(`data/element-harvest/inspections/<名前>.md`)を Read で読み、末尾の「## 報告」を Edit で埋める。
   - 回の名前を選ばなくてよい(作り直した回・古い回は道具が頁ごとに新しい方だけ拾う)。「まだ点検していない頁が無い」と出たら、そう報告して終わり。
   - 「機械で数えた分」(多い語・票だけの語・似た語の組・ジャンル案の数)は道具が全頁で数えてある。数え直さない。読んで判断するのは抜き取りの30頁だけ。
   - 型ごとに「件数 / 題・語・根拠の文」を1行ずつ。無い型は「なし」。表が0語の頁は隠しの語が根拠つきで出ているので、芯が隠れていないかを見る(型6)。
   - `[表・上げ]` = 表が0語になる頁で、道具が表に上げた語(最大3語)。 2回とも「在る」と読んだ語(r0.7)、または片方の回だけが「芯」と挙げ、もう片方は挙げなかった語(r0.8)。 これが芯から外れていれば型3〜5のどれかに書く。
   - 表が0語の頁は「抜き取り」の [隠・在る] の行で見分ける(表の行が1つも無い頁)。 型6は件数「なし」で済ませず、その頁の隠しの語を読む。
   - 書き終えたら先頭の「状態: 未記入」を「状態: 報告済み」に変える。
③ `git add data/element-harvest && git commit -m "見直しの点検: <名前>" && git push`。会話には「型ごとの件数」だけ数行で返す。

見る点 = ファイルの「報告」の見出しそのまま(その巻だけの出来事 / 語の意味違い / 宣伝文句・ありふれた語 / 根拠が支えていない / 票だけで合わない語 / 表0で芯が隠れている)。

### 点検で NEVER
- **道具・指示文・語彙・裁定ファイル(rulings.yml)を自分で直さない**。直すのは Opus(型の報告を受けて)。
- 付与案や台帳を書き換えない。`apply`・反映・デプロイをしない。
- 自分の知識で「この作品は本当は○○」と語を足さない(材料に在ることだけが根拠)。知識と食い違う時は「材料ではこう読めるが疑わしい」と報告する。
- ありふれた語の追加(表に出さず隠す語)は語ごとのユーザ裁定。候補として挙げるだけ。

## Opus 側(「見直しまとめて」= 流し切った後 /「点検なおして」= 壊れている時)
- 報告を読む = `python scripts/_element-review.py inspect --list`(状態が「報告済み」の物)→ そのファイルを Read。直し終えたら状態を「対応済み」に変え、何を直した/直さなかったかを末尾に足す。
- 判定の決まり = `_element-assign.py` の `RULES`(★その作品の語を例に書かない)/ 機械の条件 = `_element-review.py`(材料の切り方・ジャンルの条件)。直したら `VERSION` を上げる。
- 直した後の作り直し = `python scripts/_element-review.py run --redo <回の名前> --twice`。
- 直しの確かめは全件を作り直す前に、指摘された頁だけで = `run --stems <stem,stem,…> --twice`(18頁 約5分・$0.1)。2回の生の答えは各頁の `assign-answer.json` の `raw` に残る。
- 本番へ書く(`_element-assign.py apply`)はユーザの Go が要る。材料からのジャンル案を書く口は未実装(AniList 由来のジャンルだけ書ける)。
