# ジャンル・要素の全件見直し (= トリガー「見直し流して」「見直し点検して」「見直しどこまで」)

全69,556頁を1行ずつ並べた「見直しの表」の順に、手元の材料(楽天・BookLive の紹介文)を Haiku が読んで、
ジャンル・要素の**付与案**を作る。★案を作るだけ。本番データ・seed には書かない(書くのは別工程・ユーザの Go・Opus)。

- 判定は道具が Haiku を「土台なし」で直接呼ぶ。運転者(このセッション)は**コマンドを打って出力を貼るだけ**。材料を自分で読んで判定しない。
- 進み具合は台帳(`data/element-harvest/review-ledger.jsonl`)に残る。止めても次は続きから。
- 経緯・裁定・数字 = memory [[element-review-queue-state]]。判定の決まり = `scripts/_element-assign.py` の `RULES`(skill `element-assign`)。

## 「見直しどこまで」

```
python scripts/_gen-element-review-queue.py      # 表を作り直して、経路ごとの 未/案あり/適用済 を出す(約15秒)
python scripts/_element-review.py summary        # 回の一覧
```

出力をそのまま貼る。経路 = A(アニメ化あり)/ L(手元に材料あり)/ W(材料なし = ユーザ裁定で当面保留)/ 後(もう要素3つ以上)。

## 「見直し流して [件数]」(件数なし = 500)

```
python scripts/_element-review.py run --n 100 --loops <件数÷100> --twice
```

- ★60秒を超える。**background で起動し、途中で覗かない**(100件 約25分・約280万トークン。起きるのは終わりの1回)。skill `long-job-ops`。
- `--twice` = 同じ頁を2回判定させて合わせる(芯+芯・芯+在る → 表 / 片方しか挙げない語 → 隠して持つ / 材料からのジャンル案は2回とも芯の時だけ)。外さない。
- 終わったら、各回の「== 回 … の要約 ==」の行をそのまま貼り、台帳を commit+push:
  `python scripts/_gen-element-review-queue.py && git add data/element-harvest && git commit -m "ジャンル・要素の見直し: 経路L <件数>件(案のみ)" && git push`
- 「■ 中断」(モデルの失敗が3件 = 使用量の上限かもしれない)が出たら、そこで止めて報告する。叩き直さない。
- ★ユーザが自分で流す時(見張りのトークン0)= ふつうのターミナルで上のコマンドをそのまま打つ。

## 「見直し点検して」(= Sonnet の仕事。1,000件に1回が目安)

1語ずつの当否は2回判定で済んでいる。ここで見るのは**誤りの「型」**(同じ癖で何頁にも出る間違い)。

```
python scripts/_element-review.py summary                    # 回の一覧 → まだ点検していない回を選ぶ
python scripts/_element-review.py sample <回の名前> --k 30    # 30頁ぶんの「表に出す語+根拠の文」
```

見る点(当てはまる頁と語を、型ごとに並べて報告する):
1. **その巻だけの出来事**が作品の語・ジャンルになっている(長期連載の途中巻の事件・行き先・敵)。
2. **語の意味違い**(団体名・人名・題名の一部を語と読んだ。例: チーム名「○○シニア」→ シニア)。
3. **宣伝文句の語**(最強・話題沸騰 の類)や、どの作品にも当てはまる語が表に出ている。
4. 根拠の文が、その語を**支えていない**(たとえ話・脇役1人の性質・否定文)。
5. **同じ意味の語が2つ**(成長/成長物語、能力/超能力)。
6. AniList の票だけが根拠の語で、作品と明らかに合わないもの。

報告の形: 型ごとに「件数 / 実例3つ(題・語・根拠の文)」+ 30頁のうち問題なしの頁数。型に当てはまらない単発の誤りは1行ずつ。

### 点検で NEVER
- **道具・指示文・語彙・裁定ファイル(rulings.yml)を自分で直さない**。直すのは Opus(型の報告を受けて)。
- 付与案や台帳を書き換えない。`apply`・反映・デプロイをしない。
- 自分の知識で「この作品は本当は○○」と語を足さない(材料に在ることだけが根拠)。知識と食い違う時は「材料ではこう読めるが疑わしい」と報告する。
- ありふれた語の追加(表に出さず隠す語)は語ごとのユーザ裁定。候補として挙げるだけ。

## Opus 側(型の報告を受けたら)
- 判定の決まり = `_element-assign.py` の `RULES`(★その作品の語を例に書かない)/ 機械の条件 = `_element-review.py`(材料の切り方・ジャンルの条件)。直したら `VERSION` を上げる。
- 直した後の作り直し = `python scripts/_element-review.py run --redo <回の名前> --twice`。
- 直しの確かめは全件を作り直す前に、指摘された頁だけで = `run --stems <stem,stem,…> --twice`(18頁 約5分・$0.1)。2回の生の答えは各頁の `assign-answer.json` の `raw` に残る。
- 本番へ書く(`_element-assign.py apply`)はユーザの Go が要る。材料からのジャンル案を書く口は未実装(AniList 由来のジャンルだけ書ける)。
