## A. リンクの先読みで索引まで落ちる = ★想定どおり・直さない(2026-11-16 ユーザ裁定)
- ★裁定: 「総て先読みは想定通り。スマホで先読みすること自体は問題ない。進まないときの9MBを考慮するより使う前提でレスポンスが良い方法を試してこうなった」
  = 止める案(全部/スマホだけ)は不採用。**蒸し返さない** → [[feedback_prefetch_is_intended]]。私は当初これを「最大の発見(無駄)」として報告した(誤り)。
- 仕組み(事実として残す): `preload()` を頁のサーバ部品で呼ぶと、配信HTMLだけでなく `.txt`(RSC)にも先読み指定(`:HL[...]`)が入る。
  Next は画面に見えた `<Link>` の `.txt` を先読みし、その時点で指定が働く = 行き先を開く前に索引が落ち始める。
  `out/compass.txt` = head/cols/catch/hidden の4本、`shelf.txt`・`browse.txt`・`list.txt` = cols。
  ★先読みを効かせ続けるには: ヘッダーのリンクを `<Link>`(先読みあり)のままにする・頁側の `preload()` を残す。どちらかを変えると先読みが黙って止まる。
- 量: スマホ幅・初回の作品頁1枚で 索引 9.1MB(cols 4.7 + catch 3.6 + hidden 0.8)が裏で落ちる。別名索引(1.7MB)は対象外(検索した時に取る)。
- 効き目の実測(`run_tradeoff.py`・作品頁を20秒見てからヘッダーを押す・CPU4倍遅い・押してから全部そろうまで・ぶれ ±1秒):
  | 回線 | 検索 先読みあり→なし | 羅針盤 先読みあり→なし |
  |---|---|---|
  | ふつう 40Mbps | 7.8→8.2秒 | 6.4→7.8秒 |
  | 遅め 9Mbps | 7.9→12.0秒 | 5.1→14.4秒 |
  = 遅い回線ほど先読みが効いている(検索 −4秒・羅針盤 −9秒)。
- 先読みが済んだ後に残るのは端末の計算(解析・復元・下ごしらえ・描画)だが、**ユーザの実機では 検索 1.5〜3秒・羅針盤 1.2〜2.2秒**(4倍模擬の 8秒・6秒は水増し)= 急ぐ理由は薄い。

## B. 羅針盤
- 入口の輪が出るまで: 制限なし初回 2.3秒 / スマホ相当 初回 **16.6秒**・再訪 **5.9秒**(再訪はほぼ計算: cols解析0.9 + 復元1.5 + キャッチ0.9 + buildGraph 1.0〜1.5 + 最初の周り1.0)。初回のJSON 9.3MB。
- ✅2026-11-17 直した(commit a8f7ca2f95・**2026-11-20 週次で本番公開済み**)= 下の控えの不具合2件 と 見えない「周りの本」。ユーザ「その二つだけなおして」。
  直し方 = 控えに id を持たせ、控えを書いた頁の history.state にも同じ id を印(`__cpResume`)として書く → 印が同じ頁へ戻った時だけ使う(判定は純関数 `resumeVerdict`・compass.test.ts)。
  頁が生きたまま戻った時(bfcache)は pageshow(persisted) で控えと印を捨てる。周りの本は THREADS の時は nodes に入れない(placed は jumpBack の計算用に残す)。
  手元(next dev+Edge)23項目 OK・**テスト環境(mangal-preview.pages.dev)で本物の戻る(bfcache)を含む10項目 OK**(`run_preview_verify.py`)・ベルセルクの画面の書影 21件414KB → 13件238KB。★Next は最初の描画で history.state の自前キーを残す(initial pushRef.preserveCustomHistoryState=true)= 印が読める。
- (経緯)控え(sessionStorage `mangal:compass:resume:v1`)の不具合2件(本番で再現):
  1. 「詳細」→ 作品頁 → 羅針盤リンク(`/compass?from=別の作品`)= **from が無視されて前の旅が出る**(控えが from/trail より先)。
  2. 「詳細」→ 戻る(bfcache で即復帰=良い)だと控えが消えずに残り、**1時間以内に羅針盤を開き直すと「詳細を押した時点」の旅に戻る**(新しい旅にならない)。
  直し方の型 = 控えを「同じ履歴の頁へ戻って来た時だけ」使う(history.state に印 / pageshow persisted で消す / from・trail がある時は使わない)。
- 1冊進むたびに固まる: 進むの動きが終わった直後に 0.5〜1.1秒(スマホ相当)。PC の Node 実測 = neighborhood 17〜60ms + threadEntrances 中央値68・90%点132・最大213ms + mixCounts 19〜57ms。
  主因 = threadEntrances が要素・ジャンルごとに全件を並べ替える(使うのは冊数と先頭の書影だけ)。nearMix を mixCounts と二重に計算。
- (経緯・✅上で直した)画面に出ない「周りの本」(THREADS=true で常に隠す `placed`)を書影つきで描いていた = berserk で10枚・214KB(その画面の書影 414KB の半分)。乱数300冊の平均 6.4冊。
- キャッチ索引(3.6MB)の到着を待たないと糸が張れない(対象=書影+キャッチ)。必要なのは有無だけ → 索引の `fl` に「キャッチ有り」のビットを足せば cols+hidden だけで始められる。キャッチは年々増える(47,254件・生9.7MB)。
- 隠し要素の待ち上限4秒は頁を開いた時から数える。スマホ相当で到着 2.8〜3.8秒 = ぎりぎり。もっと遅い回線では索引より先に時間切れ → その回は隠し要素なし。索引が揃ってから数えれば失わない。
- PC幅: 全画面の裏で左レールが到着先読み = 別名索引1.7MB + masters + 検索の下ごしらえ(IndexedDB まで作る)。羅針盤では PageShell がレールを出さなければ消える。
- buildGraph = PC 375ms(隠し要素なしなら158ms)が描画の中で一気に走る。
- 準備中、キャッチ到着〜真ん中の本が決まるまで札に「(紹介文はまだありません)」(スマホ相当で約1秒)。
- compass-hidden.v1.json は 0.8MB(コメントの「約0.45MB」は古い)。

## C. 検索(/browse)
- ★検索語つきで直接開く(`/browse?q=…` の共有URL・再読み込み)と**端末保存(IndexedDB の下ごしらえ)を読まないし書かない**:
  描画中の searchWithTiers → ensureHay が先に全行を同期で作り、後の prewarmSearch は「もう出来ている」で早期 return = tryAdoptCached が呼ばれない。
  PC 0.6秒 / スマホ相当 3.8秒(5.4秒の固まり1本)。結果確定まで再訪でも10.1秒。ホームから検索窓で入る経路は健全(送信後2.3秒・端末保存hit)。
- 索引が届いた瞬間の1回の描画 = PC 約1秒 / スマホ相当 3.9秒。部品(PC): 閉じている抽斗の件数集計 178ms / 著者50音 106ms(レールと /list は触るまで作らないのに /browse だけ到着と同時)/ CategoryHub 8回数え 99ms / テスト用の数え7本 97ms(本番でも走る)/ 絞り込み+並べ替え 60ms。
- 一覧のカードは既定の先読み = 100作を下までスクロールで作品頁の .txt 97本・1.2MB(105本中98本はエッジに無く R2 読み)。★先読みは想定どおり=量は問題にしない(A と同じ扱い)。
- 別名索引は毎回 取得+正規化(PC 1.2秒 / スマホ相当 3.4〜3.9秒・細切れ)= 端末保存の対象外。

## E. 全体
- ヘッダー・フッターのリンク先読み = 1頁あたり18〜25本・560〜850KB(AI書評 200KB・新刊 165KB・三世代 85KB)。★想定どおり=量は問題にしない(A と同じ扱い)。
- 配信は健全: 圧縮(ブラウザへは zstd)・ETag・304・エッジ命中・preload の二重取得なし。
- ✅事前圧縮(brotli最高品質)= **2026-11-20 週次で本番適用済み**(Worker出し直し Version 0a35212e・4本とも「使用中」・本番で br 3.45MB/ETag=元MD5 を確認)。
  ★以後は**自動**: r2-sync(週次)/ `_deploy-differential.py`(差分反映・DATA週)/ `_deploy-feature.py`(機能蒸留)が元の PUT 後に `sync_br` を呼ぶ。Worker の出し直しは今回限り(br-index.js を変えた時だけ再度)。
  ★安全弁 = 事前圧縮版の名前に元のMD5が入る → 元だけ更新されて圧縮版が古い/置き損ねた時は「見つからない」で従来の配り方に戻るだけ(取り違えは起きない)。sync_br の失敗は配信を止めない。 Worker=`workers/br-index.js`(元の隣の `<キー>.<元MD5>.br` を返す・元のETagはエッジの元の応答→無ければR2 head を60秒控え・br本体もエッジに /__br/ で焼く=定常R2ゼロ・purgeで控えも消す)。
  置く道具=`scripts/_index_br.py`(R2の元ETag==手元MD5の時だけ置く・古い版を消す・`--status`/`--remove-all`)。 r2-sync/差分反映/機能蒸留の PUT 後に自動で呼ぶ。 手元miniflareで12項目OK。
  fable 5.2 が Worker 部品を書いた所で利用上限で停止→Opus が仕上げ(旧案=毎回R2 head+getでエッジ素通り、を是正)。 実測: cols 本番zstd 4.81MB → br q11 3.45MB(圧縮32秒)。
- その場圧縮は低品質(cols 4.80MB)。事前に brotli 最高品質で置けば cols 3.45 / catch 2.64 / alt 1.34 / hidden 0.63MB = 約28%減([[search_perf_hotspots_2026_08]] の残レバーと同じ・今は4本ぶん)。
- エッジ命中の応答に `Age` が付く → ブラウザ側の `max-age`(HTML 60秒・JSON 4時間)は実質効かず毎回確認に行く。hidden は「古いのを使って裏で確認」で動く。HTML は ETag が無いので毎回取り直し。害は小さい(直すかは任意)。

**Why:** 先読みとキャッシュは何度も手を入れた所で、配線の漏れ(見えない物のために払う型)が再発しやすい。数字が無いと優先が決まらない。
**How to apply:** ユーザが「羅針盤が遅い」「本棚が遅い」「検索が遅い」等と言ったらここを起点に。直す時は該当の `run_*.py` で前後を計る。先読みの量は論点にしない([[feedback_prefetch_is_intended]])。
