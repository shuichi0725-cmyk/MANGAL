2026-11-16 ユーザ依頼「先読みしてキャッシュに蓄えている所の改善点を調査(変更なし)・検索/羅針盤/本棚の三カ所を重点」。
**コードは1行も変えていない。直すかどうかは全部ユーザ裁定待ち。**

## 計り方(直した後に同じ道具で計り直す)
- 道具 = `.cache/bench/site-measure/`(git管理外): `cdp.py`(Edgeヘッドレス+CDP の小道具)+ `run_*.py`(本番を普通の訪問者と同じ読み取りだけで計る)+ `compass-bench.ts` / `browse-bench.ts`(Node で計算時間)+ `brsize.mjs`(圧縮の見積もり)。
- 「スマホ相当」= 回線 9Mbps・往復165ms + CPU 4倍遅い(Chrome の模擬。実機の代わりの目安)。
- ★計測は本番に訪問として数えられる(11/16 は約50閲覧ぶん・UA Chrome/130)。

## A. 最大の発見: リンクの先読みが索引まで落とす(全頁・スマホも)
- 仕組み(確認済み): `preload()` を頁のサーバ部品で呼ぶと、配信HTMLだけでなく `.txt`(RSC)にも先読み指定(`:HL[...]`)が入る。
  Next は画面に見えた `<Link>` の `.txt` を先読みし、その時点で指定が働く = **行き先を開いていなくても索引を取りに行く**。
  `out/compass.txt` = head/cols/catch/hidden の4本、`shelf.txt`・`browse.txt`・`list.txt` = cols。
- 実測: スマホ幅・初回の `/manga/berserk` = 合計 **10.5MB、うち 9.1MB(86%)がこの頁で使わない索引**(cols 4.7 + catch 3.6 + hidden 0.8)。
  `/browse` や `/shelf` でも hidden 0.8MB が落ちる。しかも hidden は優先度 High で、その頁に要る cols(Low)より先に通る。
- 2026-09-08 の裁定「検索する気のない訪問者に数MBを落とさない」(モバイルは完全休止)が、この経路で破れている(9/23 の preload 導入〜)。
- 最小の直し方 = GlobalNav の 検索・羅針盤・本棚(+フッターの一覧表)の `<Link>` を `prefetch={false}`。押した時に `.txt` を取る分だけ遅くなる(0.1秒台)。
  代案(未検証)= `preload()` をやめて JSX の `<link rel="preload">` にする(.txt に指定が入らないはず。要ビルド確認)。
- 規模: 週 約1,500訪問・5,500閲覧 = 費用には響かない(R2の転送は無料)。害は訪問者のスマホ通信量と回線の取り合い。
- ★止めた時の代償(2026-11-16 ユーザ質問「やめたら遅くならない?」→ 実測 `run_tradeoff.py`): 今の先読みは、結果として
  「初めて来て 検索/羅針盤 へ進む人」の索引を先に落としている = 止めるとその人だけ遅くなる(同じ週の再訪は端末に残るので不変・週次で索引が替わった後の最初の1回は同じ)。
  作品頁を20秒見てからヘッダーを押す・CPU4倍遅い・押してから全部そろうまで(計測のぶれ ±1秒):
  | 回線 | 検索 今→止めた後 | 羅針盤 今→止めた後 |
  |---|---|---|
  | ふつう 40Mbps | 7.8→8.2秒(+0.4) | 6.4→7.8秒(+1.4) |
  | 遅め 9Mbps | 7.9→12.0秒(+4.1) | 5.1→14.4秒(+9.3) |
  ほかに押した瞬間の切り替えが +0.1〜0.3秒(.txt を押してから取る分)。作品頁の通信は 10.3MB→1.4MB。
  折衷 = スマホだけ止めて PC は今のまま(9/8 の裁定「PCは到着で先読み・モバイルは休止」と同じ線引き。常に `prefetch={false}` にして PC幅の時だけ `router.prefetch`)。
  ★裁定待ち(全部止める / スマホだけ / そのまま)。

## B. 羅針盤
- 入口の輪が出るまで: 制限なし初回 2.3秒 / スマホ相当 初回 **16.6秒**・再訪 **5.9秒**(再訪はほぼ計算: cols解析0.9 + 復元1.5 + キャッチ0.9 + buildGraph 1.0〜1.5 + 最初の周り1.0)。初回のJSON 9.3MB。
- ★控え(sessionStorage `mangal:compass:resume:v1`)の不具合2件(本番で再現):
  1. 「詳細」→ 作品頁 → 羅針盤リンク(`/compass?from=別の作品`)= **from が無視されて前の旅が出る**(控えが from/trail より先)。
  2. 「詳細」→ 戻る(bfcache で即復帰=良い)だと控えが消えずに残り、**1時間以内に羅針盤を開き直すと「詳細を押した時点」の旅に戻る**(新しい旅にならない)。
  直し方の型 = 控えを「同じ履歴の頁へ戻って来た時だけ」使う(history.state に印 / pageshow persisted で消す / from・trail がある時は使わない)。
- 1冊進むたびに固まる: 進むの動きが終わった直後に 0.5〜1.1秒(スマホ相当)。PC の Node 実測 = neighborhood 17〜60ms + threadEntrances 中央値68・90%点132・最大213ms + mixCounts 19〜57ms。
  主因 = threadEntrances が要素・ジャンルごとに全件を並べ替える(使うのは冊数と先頭の書影だけ)。nearMix を mixCounts と二重に計算。
- 画面に出ない「周りの本」(THREADS=true で常に隠す `placed`)を書影つきで描いている = berserk で10枚・214KB(その画面の書影 414KB の半分)。乱数300冊の平均 6.4冊。
- キャッチ索引(3.6MB)の到着を待たないと糸が張れない(対象=書影+キャッチ)。必要なのは有無だけ → 索引の `fl` に「キャッチ有り」のビットを足せば cols+hidden だけで始められる。キャッチは年々増える(47,254件・生9.7MB)。
- 隠し要素の待ち上限4秒は頁を開いた時から数える。スマホ相当で到着 2.8〜3.8秒 = ぎりぎり。もっと遅い回線では索引より先に時間切れ → その回は隠し要素なし。索引が揃ってから数えれば失わない。
- PC幅: 全画面の裏で左レールが到着先読み = 別名索引1.7MB + masters + 検索の下ごしらえ(IndexedDB まで作る)。羅針盤では PageShell がレールを出さなければ消える。
- buildGraph = PC 375ms(隠し要素なしなら158ms)が描画の中で一気に走る。
- 準備中、キャッチ到着〜真ん中の本が決まるまで札に「(紹介文はまだありません)」(スマホ相当で約1秒)。
- compass-hidden.v1.json は 0.8MB(コメントの「約0.45MB」は古い)。

## C. 検索(/browse)
- ★検索語つきで直接開く(`/browse?q=…` の共有URL・再読み込み)と**端末保存(IndexedDB の下ごしらえ)を読まないし書かない**:
  描画中の searchWithTiers → ensureHay が先に全行を同期で作り、後の prewarmSearch は「もう出来ている」で早期 return = tryAdoptCached が呼ばれない。
  PC 0.6秒 / スマホ相当 3.8秒(5.4秒の固まり1本)。結果確定まで再訪でも10.1秒。ホームから検索窓で入る経路は健全(送信後2.3秒・端末保存hit)。
- 索引が届いた瞬間の1回の描画 = PC 約1秒 / スマホ相当 3.9秒。部品(PC): 閉じている抽斗の件数集計 178ms / 著者50音 106ms(レールと /list は触るまで作らないのに /browse だけ到着と同時)/ CategoryHub 8回数え 99ms / テスト用の数え7本 97ms(本番でも走る)/ 絞り込み+並べ替え 60ms。
- 一覧のカードは既定の先読み = 100作を下までスクロールで作品頁の .txt 97本・1.2MB(105本中98本はエッジに無く R2 読み)。
- 別名索引は毎回 取得+正規化(PC 1.2秒 / スマホ相当 3.4〜3.9秒・細切れ)= 端末保存の対象外。

## D. 本棚
- 17冊の棚: 巻数・続きの巻が全部そろうまで 制限なし 1.4秒 / スマホ相当 初回 **14.5秒**・再訪 **4.0秒**。段と一部(上位100作・版つき)は先に出る。
- 数冊のために cols 4.7MB + catch 3.6MB を読む。再訪が主用途なので、棚の控え(今は題名・書影)に巻数・状態・キャッチ・著者も持たせれば即表示→裏で更新にできる。
- 版つきの1冊ごとに vc の1本(65〜72KB)を読む(欲しいのは巻数と1巻の書影の2つだけ)。

## E. 全体
- ヘッダー・フッターのリンク先読み = 1頁あたり18〜25本・560〜850KB(AI書評 200KB・新刊 165KB・三世代 85KB)。羅針盤は全画面なのにフッターまで全部先読み。
- 配信は健全: 圧縮(ブラウザへは zstd)・ETag・304・エッジ命中・preload の二重取得なし。
- その場圧縮は低品質(cols 4.80MB)。事前に brotli 最高品質で置けば cols 3.45 / catch 2.64 / alt 1.34 / hidden 0.63MB = 約28%減([[search_perf_hotspots_2026_08]] の残レバーと同じ・今は4本ぶん)。
- エッジ命中の応答に `Age` が付く → ブラウザ側の `max-age`(HTML 60秒・JSON 4時間)は実質効かず毎回確認に行く。hidden は「古いのを使って裏で確認」で動く。HTML は ETag が無いので毎回取り直し。害は小さい(直すかは任意)。

**Why:** 先読みとキャッシュは何度も手を入れた所で、配線の漏れ(見えない物のために払う型)が再発しやすい。数字が無いと優先が決まらない。
**How to apply:** ユーザが「先読みの件」「羅針盤が遅い」「本棚が遅い」等と言ったらここを起点に。直す時は該当の `run_*.py` で前後を計る。
