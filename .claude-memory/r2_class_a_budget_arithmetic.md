## なぜ毎回18万なのか

バケット = **185.15k オブジェクト = 約92,000ルート × 2(`.html` + RSC `.txt`)**。
全ページHTMLに共通シェルのチャンクハッシュが埋まるので、**layout に載る物を1行触ると全ページのバイトが変わり全量PUT**。
逆に、シェルを触らない週は全量にならない(DATA週 = 数千オペ)。ETag実物照合でPUT省略は実装済みだが、
本当に全部変わる週は省略が効かない(2026-09-08 夜は「同一0キー」)。

## 効く順のレバー

1. ★**シェル改修は preview で回す = R2費用ゼロ**。preview は `wrangler pages deploy`(mangal-preview.pages.dev)で
   **R2バケットを一切使わない**。試行錯誤は何回でも0オペ。費用が出るのは本番へ出す1回だけ。
2. **本番へ出す回数**。フル5回=915k(天井)/ フル1回+DATA週4回=約190k(枠の19%)。
   今の高止まりは「2週間シェルを本番で反復した」結果で、恒久的な床ではない。
3. `.txt`(RSC)を出さない = オペ半減(92,000減)。ただしクライアント遷移が全ページ再読込に落ちる = **推さない**。
4. ★**masters 是正(容量9.9GB削減)は Class A を減らさない**。オブジェクト数が変わらないため。
   減るのは容量・転送量・同期時間 → [[shell_props_serialized_to_all_routes]]

## 判断の型

「$4.50かかる?」と聞かれたら**まず台帳を期で集計**する(体感で答えない)。
余白 = 1,000,000 − 当期累計 − (残り週次回数 × 183,000)。**余白がフル1回分(183k)を切ったら**
「今期はもう追加の本番同期をしない」を提案する。2026-09-09時点の今期は余白86,000 = 1回分未満だった。
