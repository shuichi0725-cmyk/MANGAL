調査系の一括作業で **N頁 × エージェント** のファンアウトを組むとき、**全件を同じ濃度で投げてはいけない**。
機械的に計算できる証拠を先に一括で出し、**証拠が割れた分だけ**AIに回す。

**Why:** 2026-08-28、刊行run分裂59頁の裏取りで **サブエージェント202体 / 約590万トークン / ツール実行989回** を使い、
ユーザに「今回トークンの使用料が激しい。何が今までと違う？」と指摘された。普段のper-case作業はサブエージェント0体。
★決め手になった証拠の大半(MADBのシリーズ容器ID `schema:isPartOf` / 楽天seriesName / ISBN連番 / 発売日の単調性)は
**全部が機械計算できるもの**だった。それを**59体が各々1.2GBの楽天キャッシュと668MBのMADB rawを舐め直した**のが本体。
同じスキャンを59回やった。反証役を別に立てて約2倍にしたが、覆ったのは56件中1件。

**How to apply:**
- ★**濃度を機械証拠の合致度で振り分ける**。①全件ぶんの機械証拠を**1本のスクリプトで一括算出**(キャッシュは1パス走査)
  → ②全会一致は自動確定 → ③割れた分(今回なら15件前後)だけエージェントに投げる。これで数十分の一。
- ★**同じ重いファイルを各エージェントに舐めさせない**。共有の中間成果(`.cache/<topic>-*.json`)を親が先に作って渡す。
- ★反証役の二段構えは**全件でなく、機械証拠が薄い/矛盾する件だけ**に掛ける。
- ★**エージェントに渡すリストは投げる前に検算**する。今回スライスのミスで3体が対象外slug
  (akabee/arabesuku/bangai-koshien)を渡され、丸ごと無駄になった。
- ★**セッション上限で落ちると再開でもう一度払う**。大きなファンアウトは上限に近い時間帯に始めない。
- ★重い生成作業(エンリッチ1,071作=キャッチ+あらすじ2,140本)と大規模ファンアウトを**同一セッションに同居させない**。
- ワークフロー起動は ultracode か明示指示がある時だけ。有効でも「やってよい」であって「やるべき」ではない。

## 再発(2026-09-01): レビュー用ワークフローで**セッション上限**に当たった
- /shinkan静的化のレビューを「5レンズ+指摘ごとに反証2体」で組み、17体・71万tokで**セッション上限(5時間枠)に到達**し16体が失敗。2回目もユーザが使用状況画面(セッション45%・Fable週30%)を見せて「このやり方終わる？」と懸念→停止し手元確認に切替。
- ★ユーザは**使用量上限を気にしている**。ultracode指示があっても、コード変更のレビューは**レンズ1〜2本+反証1体まで**。指摘の裁定は自分でコードを読めば足りることが多い(今回も残り2レンズは手元で数分)。
- 長時間の並走(ビルド等ローカル処理)はトークンを使わない=「終わる？」への答えは「残りはローカル処理だけ」と即答できるようにしておく。
