速さの調査で、Chrome/Edge の「CPU を N倍遅くする」模擬の秒数を、較正なしに「スマホ相当」と呼んで報告しない。

**Why:** 2026-11-16 の先読み・キャッシュ調査([[prefetch_cache_audit_2026_11_16]])で「CPU 4倍遅い」を「スマホ相当」として
「検索は押してから約8秒・羅針盤5〜6秒」と報告 → ユーザ「スマホで使ってそんなにかからないよ?何かおかしい」。
較正したら、ユーザの実機は**このPCの1〜1.5倍**相当だった(2026-08-01 の実機記録 デコード218ms ⇔ このPC 1倍 約225ms)。
同じ流れを計り直すと 検索 1.5〜3.0秒・羅針盤 1.2〜2.2秒(うち1秒は準備中アニメの最低表示)= 報告は3〜5倍の水増しで、
それを根拠に「固まる」「遅い」と改善候補の重さまで盛っていた。4倍は Lighthouse 由来の「古い低価格機」の設定で、根拠なく採った。
[[search_perf_hotspots_2026_08]] に「実機の数字は #debug の診断で採る。PCの実測だけで議論すると桁が合わない」と書いてあったのに使わなかった。

**How to apply:**
- 体感の秒数を言う時は **CPU 1倍 と 1.5倍** で計る(= ユーザの実機の幅)。4倍は「古い低価格機の最悪値」と明記した時だけ添える。
- 較正の物差し = 実機の診断行(`/browse#debug` をスマホで開くと出る「診断 索引: 取得…/デコード…/検索…/別名…」)。
  秒数が判断の決め手になる時は、まずこの行をユーザにもらうか、記憶の実機記録と同じ項目を同じ流れで計って倍率を出す。
  道具 = `.cache/bench/site-measure/run_calib.py`。
- 模擬で言えるのは「どの部品が相対的に重いか」。「何秒待たされるか」は較正してから。
- ユーザの体感と数字が食い違ったら、サイトより先に自分の計り方を疑う([[feedback_absence_needs_verification]] と同じ向き)。

## 2026-11-16 23:55 実機の診断行で確定
ユーザがスマホで `/browse#debug` を開いた診断 = **取得590ms / デコード256ms**(検索語なし・70,018件)。
同じ流れのこのPC(`run_calib2.py`): 1倍 = 取得469〜544 / デコード211〜242、1.25倍 = 695〜745 / 262〜319、1.5倍 = 810〜829 / 298〜301。
→ **ユーザの実機 ≈ このPCの 1.1〜1.2倍**。体感の秒数は CPU 1倍(少し足す)で読むのが正しい。
- ★診断の行は**描画した時点の値で止まる**(後から埋まる「空き時間」「端末保存」は表示が更新されない = 実機の写真で「空き時間2ms(100行)・端末保存–」でも故障ではない)。
  端末保存や検索・別名の欄は、検索を1回してから読む。倍率の較正には「デコード」を使う(通信が混ざらない)。
