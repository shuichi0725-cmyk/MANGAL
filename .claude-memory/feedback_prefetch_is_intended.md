先読み(ヘッダーのリンクの先読み → 行き先の `.txt` の先読み指定が働いて索引が落ちる経路を含む)は**全部想定どおり**。
スマホでも先読みしてよい。「進まない時の通信量(9MB)」は考慮の対象にしない。

**Why:** ユーザの言葉(2026-11-16)=「総て先読みは想定通り。スマホで先読みすること自体は問題ない。進まないときの9mを考慮するより
使う前提でレスポンスが良い方法を試してこうなった」。私は [[prefetch_cache_audit_2026_11_16]] で、これを「一番大きい発見(無駄な9MB)」として
先頭に報告し、止める案(全部/スマホだけ)まで出した。根拠にしたのは 2026-09-08 のメモ「検索する気のない訪問者に数MBを落とさない・モバイルは休止」
([[search_perf_hotspots_2026_08]])と `lib/preloadIndex.ts` の注記だったが、あれは**見えない左レールのための計算(下ごしらえ3.7秒)**を止めた話で、
通信の先読みを禁じたものではなかった = 古いメモを今の方針として読み違えた。

**How to apply:**
- 性能の点検で、先読みで落ちるバイト数を「無駄」として数えない・止める提案をしない(ヘッダー/フッター/カードのリンク先読みも同じ扱い)。
- 提案するのは「使った時のレスポンスが良くなること」: 押した後の端末の計算(解析・復元・下ごしらえ・描画)を減らす、先読みが早く終わるようにする(圧縮)、先読みの対象に足りない物を足す、など。
- 2026-09-08 の「モバイルは休止」を引く時は「計算の話」とだけ読む。通信の先読みに広げない。
- 実測の参考: 先読みが済んでいても、押してから全部そろうまで スマホ相当で 検索 約8秒・羅針盤 5〜6秒 = 残りは端末の計算([[prefetch_cache_audit_2026_11_16]])。
