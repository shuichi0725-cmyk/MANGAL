2026-09-09。本番の検索不調の調査で、**否定的な観測を鵜呑みにして続けて2回誤った**。

## 実際にやった間違い

1. **`isFullIndexLoaded` を `app/HomeClient.tsx` で grep → 3箇所しか出ない → 「/browse には /list のような読込中ガードが無い」と結論。**
   → **誤り**。ガードは `useFilterPanelData` の `searchPending` 経由で**存在した**(`HomeClient.tsx:500`
   `indexLoading || searchLoading || (searchPending && paged.length === 0)`)。
   しかも「散々テストしたのに」というユーザの申告に対し、**存在しない不具合**を原因として提示してしまった。

2. **prune 済チャンクを `while read` で curl → `000` が返る → 「消したJSが404してhydrationが失敗」と結論。**
   → **誤り**。`.cache/r2-pruned-*.txt` が CRLF で、URL末尾に `\r` が付いて壊れていただけ。実際は **200**。

## 一般形

**否定の証拠は肯定の証拠より壊れやすい。**「見つからない / エラーコード / 空 / 0件」を根拠にする時は、
**観測手段そのものを先に検算する**:
- grep で「無い」→ 別名・間接経由(hook/props/再エクスポート)を潰したか。**呼び出し側から辿り直す**。
- 異常な応答コード(`000` 等)→ まず**リクエストが正しく組めているか**(改行コード・引用符・エンコード)。
- 「一致しない」→ 比較対象が本当に同じ物か(単位・MiB/MB・圧縮前後)。

肯定の証拠(md5一致・実ヘッダの値・負テストで落ちること)は壊れにくいので、**そちらを先に取りに行く**。

## ★ユーザの「テストした」は証拠

「散々テストして今回それを直すために週次蒸留したんだけど?」への正しい応答は、
**テストを疑うことでも、テストを説明して退けることでもなく、両方が成り立つ説明を探すこと**だった。
実際の答えは [[preview_deploy_pitfalls]] の規模差(テスト0.50MB / 本番9.85MB = 約20倍)で、
**テストは正しく、本番の問題も本物**だった。ユーザの申告を制約条件として扱うと正解に速く着く。


## ★続報(2026-09-10): 負テストは「効かない修正」も炙り出す

検出器#30の穴を塞ぐのに**2箇所直したつもり**だったが、負テストで片方が無駄と判明した。

## ★2026-09-18 追記: 「緑」も否定の観測である。対照群で**道具を検定**してから信じる

同じ日に**3回**踏んだ。いずれも「道具が問題なしと言った」ケース = 上の一般形の別の極性。

1. **番人 `_check-ssr-content.py` が FAIL 0 を出していた** → 実際は5コーナーが空HTMLで公開中。
   原因は床150字が共通シェル363字より低く、**中身ゼロでも必ず通る**設計だったこと。
   → [[ssr_content_gate]]
2. **自作の監査スクリプトが「中身が空の頁 0件」** → 判定条件を `内容リンク==0` にしたが、
   **共通シェル自身が内容リンクを1本持って**いたので永遠に成立しなかった。
3. **`urllib.robotparser` が `/browse?author=` を「許可」と判定** → robots.txt の書き方が悪いのかと
   疑ったが、**対照に入れた既存の `Disallow: /data/`(2026-08-17から稼働中)まで「許可」と出た**。
   → 犯人は robots.txt ではなく**パーサ**だった: `urllib.robotparser` は**先勝ち**なので
   先頭の `Allow: /` で全部通る。**Google は最長一致(most specific)が勝つ**。
   Google準拠の評価器を書き直したら全件期待どおりになった。

## ★手口: 対照群(既知の陽性)を必ず混ぜる

道具が「問題なし」を返した時、それが
 (a) 本当に問題が無い のか
 (b) **道具が問題を見つけられない** のか
は、出力だけでは区別できない。**既に正しいと分かっている陽性・陰性を検査対象に混ぜる**と一発で割れる。

- 番人 → 「壊した頁を作って落ちるか」を実演する(負テスト)。旧実装で素通りすることも示す。
- robots.txt → **既存の稼働中ルール**を評価ケースに入れる。それが落ちなければ道具が壊れている。
- 監査スクリプト → 既知の不良1件と既知の正常1件を先に通して、期待どおり分かれるか見る。

★閾値・判定条件を書いたら「**この条件は守る対象より厳しいか**」を数字で確かめる
(床150 < シェル363 が全ての元凶だった)。
